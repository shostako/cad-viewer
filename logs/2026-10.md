### 技術的な発見
- ボール法の偽の薄い値の仕組み: 頂点で接する球は、頂点を通る隣の面に t(1 − cos θ) 食い込む。球が入るかの判定に許容 tol があると、半径 tol / (1 − cos θ) まで「入る」ことになり、壁の厚さと関係ない値が出る（箱の稜線で 0.0015 mm、円筒の 32 分割で 0.1 mm）。見分けは「止めた三角形が頂点を通るか」。距離で見る（1.2t など）と、45° の面取りのそばで正しく止まった球（当たった点は 0.76t）まで消す
- OCCT の `Extrema_ExtCC` は、円どうしで最小の組しか返さない（最大の候補にならない）。最大は刻んでから、`Extrema_ExtPC`（点と曲線の極値をすべて返す）を交互に使って詰める
- 円筒の縁の点が継ぎ目の端にあると、2 本の稜線にかかる。テストで稜線を点から探すときは継ぎ目から外す
- 計測の 1 点目の案内は、面積などの答えが来ると書き直される（#62 から）。案内の文を決め打ちで比べるテストは、答えの速さで落ちる（CI の e2e (1) の c13）
- 肉厚の答えを「頼んだ側」で覚えると、置いていかれたヒートマップの答えまで残り、次にヒートマップを入れたとき計算が走らない（c5 が落ちた）。答えは使う側が覚える

- Vite を動かしたまま src を書き換えると、`?t=` 付きの新しいモジュールと元のモジュールが二重になる。テストが `import('/src/picking.ts')` で差し替えた prototype が、アプリでは呼ばれない（test_hover_preselect の (n2) が「pick の記録が 0 件」で落ちた）。rebase でなくても起きる
- Write で書いた `'\ufeff'` が、エスケープでなく U+FEFF の文字そのものとしてファイルに入った（ツールの引数は JSON で、`\uXXXX` が解かれる）。動きは同じなので気づかず、変異の置き換え文字列が当たらなくて分かった。Bash の heredoc で書いた文も同じで、このログの下書きにも入っていた
- `pkill -f` の文字列が自分のシェルのコマンドにも当たり、そのシェルが終了コード 144 で死んだ（記憶にある罠をまた踏んだ）。プロセスは `ps` で探して pid で止める
- OCCT の `STEPControl_Writer` は、作った時点で `write.step.unit` の既定を入れ直す。`Interface_Static.SetCVal_s("write.step.unit", "INCH")` は writer を作ってから呼ぶ（先に呼ぶと mm で書かれる）
- Chromium は印刷（`page.pdf`）で、`thead` を各ページの頭に出す。CI に PDF を読む道具（PyMuPDF）が無いので、ページの頭の見出しは手元だけで見て、CI ではページが増えることだけを見る
- Playwright の `wait_for_url("blob:*")` は、glob の `*` が `/` に当たらないので blob の URL を待てない。述語（`lambda u: u.startswith("blob:")`）で待つ
- Excel（手元の Windows の Excel、win32com の DispatchEx）で記録の CSV を開いて確かめた。日本語は化けず、コメントの改行と読点は 1 つのセルに入り、数は数・日時は日付として読まれる
- 手元の E2E を 3 本並列で回すと、本の数が変わるたびに同時に走る組が変わる。共有の mini_mold.step のサイドカーを使う test_sidecar_flush と test_sidecar_isolation が同時になると、flush が落ちる（単独では通る）。CI はジョブごとに backend が別なので起きない
- 変異の道具を前のものから写して作ると、同じ名前の定数（`PR` など）が後ろの定義で上書きされ、別のファイルを壊していた（変異が「当たらない」と出た）。名前は道具ごとに分ける
- 「欄の中の Esc」の変異は、アプリ全体のキーの処理（欄の外の Esc）が閉じてしまうと生き残る。欄にフォーカスを置いて押す確かめが要る
- 直線の稜線の向きを表裏で入れ替える処理は、どのテストでも見分けられなかった（変異が生き残った）。決め方の違いでしかないので消した

### 記憶候補
- Vite の二重モジュールは rebase に限らない（記憶を更新済み）
- Write の `\uXXXX` は文字そのものになる（記憶に足した）
